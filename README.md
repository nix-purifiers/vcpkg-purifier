# vcpkg-purifier

Locked, Nix-resolved dependencies for vcpkg and CMake projects.

## Quickstart

From a project with `vcpkg.json` and `CMakeLists.txt`:

```sh
nix shell 'github:nix-purifiers/vcpkg-purifier'
vcpkg-purifier lock
vcpkg-purifier prefetch
cmake -S . -B build \
  -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
cmake --build build
ctest --test-dir build --output-on-failure
```

Commit `vcpkg-lock.json` and `vcpkg-purifier.lock.json`.
The first exports vcpkg's native registry lock; the companion records selected
recipes, source archive hashes, features, and project configuration.
`lock` runs a native dependency installation to capture the required downloads.
`prefetch` builds those dependencies in Nix and roots their environment and the
compiler/editor toolchain against garbage collection.

The supplied `vcpkg` and `cmake` wrappers are required to activate the locked
environment. They use a private installed prefix under `.vcpkg-purifier` and
leave an existing `vcpkg_installed` tree alone. The shell also provides the
compiler, build tools, `ctest`, and `clangd`. You can install the package through
your usual Nix configuration instead of entering a shell each time.

Without a lockfile, wrappers warn and run the ordinary, impure tool, preserving
arguments, streams and exit status. A stale or invalid lock fails and asks you
to run `vcpkg-purifier lock`; it never silently falls back to online resolution.

## Updating dependencies

```sh
vcpkg-purifier update zlib
vcpkg-purifier update
```

Updates use vcpkg's native registry baseline updater. A named update preserves
the other selected versions through native manifest overrides. A full update
removes those automatically managed overrides, while retaining overrides you
wrote yourself. In-tree updates retain the native updater's manifest and
configuration edits; commit them with the lockfiles.

`lock` retains saved registry references even with an empty local Git cache.
It can repair a damaged companion from native pins, or recover damaged native
pins from an unchanged companion.

Select optional native manifest features when locking:

```sh
vcpkg-purifier --feature tools lock
vcpkg-purifier prefetch
```

The lock holds separate profiles for x86-64 and ARM64 Linux. Run `lock` on each
platform you use to add its native dependency graph. Changes to project
configuration invalidate the other profiles until they are refreshed there.

## Editor

Use the supplied `clangd` with the compile commands generated by CMake:

```sh
clangd --compile-commands-dir=build
```

The CMake wrapper supplies the locked dependency paths and SDK. Existing
arguments selecting vcpkg's standard CMake toolchain or the recorded triplet
are accepted. A different toolchain, feature set, or installed prefix needs
explicit integration rather than silently changing the dependency graph.

## External locks and Nix builds

Locks may live outside the working copy:

```sh
vcpkg-purifier \
  --lockfile ../locks/vcpkg-purifier.lock.json \
  --native-lock ../locks/vcpkg-lock.json lock
vcpkg-purifier \
  --lockfile ../locks/vcpkg-purifier.lock.json \
  --native-lock ../locks/vcpkg-lock.json prefetch
```

A new external native lock starts from the working copy's saved registry pins.
External updates leave its native manifests and lockfiles unchanged. Set
`VCPKG_PURIFIER_LOCKFILE` and `VCPKG_PURIFIER_NATIVE_LOCKFILE` to select these
locks for the normal wrappers.

Apply `overlays.default` and call the scoped builder for a sandboxed project
build:

```nix
pkgs.vcpkg-purifier.buildVcpkgProject {
  src = ./project;
  lockFile = ../locks/vcpkg-purifier.lock.json;
  vcpkgLock = ../locks/vcpkg-lock.json;
}
```

The result exposes `packages.project`, `packages.environment`, `tests`,
`release`, and `fetches`. The project builder configures, builds, tests and
installs through CMake. `cmakeFlags`, `buildTargets`, `test`, `nativeBuildInputs`,
`srcFilter`, and caller-supplied `fetchers` customize it. Source releases are
deterministic tarballs containing the selected locks.

Publish that Nix-built source archive to a GitHub release with:

```sh
vcpkg-purifier publish \
  --repo OWNER/PROJECT --tag v1.0.0
```

`lib.vcpkg-purifier.readLock` reads both locks into the shared entry/output/
problem shape without import-from-derivation. Archive entries carry their native
SHA-512 byte hashes. Selected recipes are exported losslessly, including binary
files and executable modes; local overlay changes invalidate the lock.

## Supported scope

Native Linux `x64-linux` and `arm64-linux` triplets are supported, using public
HTTP(S) SHA-512-tagged source assets. Built-in and Git registries, local filesystem
registries, and project-relative overlay ports are resolved by native vcpkg.
Declare overlays in project configuration; ambient overlay and feature flags
are excluded from locked commands.
Local recipe changes are locked with `lock`; named updates of local overlays
and filesystem registries are not yet supported.

Ports that clone source repositories directly or perform other untracked
downloads cannot currently be replayed by the asset transport and fail during
the sandboxed prefetch. Cross-compilation, custom triplets, legacy `CONTROL`
recipes, and different host/target recipes for the same port are not supported
yet. vcpkg has no suitable project autoload plugin for this integration, so
there is no separate native plugin package to install.

## Native libraries and installed resources

Declare public installed shared libraries with `nativeLibraries`, for example
`nativeLibraries.proof = "lib/libproof.so";`. Use the host platform shared-library
suffix for portable packaging. `nativeIncludeDirectories = [ "include" ];`
records public header directories. The result and `packages.project` expose
`projections.native`, `python-ffi`, and `java-ffi`, using the shared binary ABI
validator and native loader interfaces. Only deliberately exported C interfaces
should be selected; the adapter does not infer symbol signatures or convert
C++ classes into a foreign ABI. Runtime libraries must remain in the producer's
Nix closure.

`resourceRoots` maps public resource paths to installed producer paths; for
example `resourceRoots."proof.h" = "include/proof.h";`. Its `resources`, `web`,
and `java-resources` projections expose `.directory`, `.documentRoot` and
`.classPath`. Optional `resourceDependencies` and `resourceSchema` use the
shared resource bundle contract. Selections default to empty, and do not
publish source/configuration files automatically. Schema format/entrypoints
are caller declarations; this builder does not infer or compile an IDL.

The consumer check builds an actual C API shared target against the locked
zlib dependency. Ordinary Python ctypes, Python cffi reading the public
header, and Java FFM call the function; dladdr independently checks its origin.
The selected header is also loaded through ordinary HTTP and Java resources.
Java21 uses preview FFM flags. No additional target/platform coverage or
language-specific binding package is implied.
